# LEO知识库数据管理规范

> 本文规定字段、类型、日期、标签、结构化记录、内容质量和数据安全。目录及正文组织见 [[文件架构和文档内容结构设计]]，建设原则见 [[LEO知识库构建思路]]。

## 1. 适用范围

本规范用于新建正式笔记，以及经过整理的旧笔记。Inbox 临时速记可以先写正文，转为正式内容时再补齐信息。历史笔记和现有模板不自动视为符合本规范。

“必填”表示正式笔记最低要求；“按需”表示只在有对应含义时填写。不要为填满属性而编造日期、来源、数值或结果。

## 2. 文件与 YAML 格式

- 正文使用 UTF-8 Markdown；换行风格在同一文件中保持一致。
- YAML 属性区置于文件最顶部，由独立一行的 `---` 开始和结束。
- 字段名使用下表给出的英文名称，不以多个同义名称表示同一个字段。
- 缩进使用空格；列表使用多行形式；禁止重复字段名。
- 内部链接作为属性值时用引号包裹；包含冒号等特殊字符的字符串也使用引号。
- 没有数据的可选字段直接省略，必要时用 `null`；空列表用 `[]`。不要用空字符串、破折号、`未知` 混充日期或数字。

## 3. 通用字段字典

| 字段 | 类型 | 要求 | 含义 |
| --- | --- | --- | --- |
| `title` | 字符串 | 必填 | 文档主题；可比文件名更具体 |
| `type` | 枚举字符串 | 必填 | 文档用途，取值见下文 |
| `created` | 日期 | 必填 | 此笔记实际创建日期，不是事件发生日期 |
| `updated` | 日期 | 按需 | 实质内容最近更新日期；规范、项目说明和模板应填写 |
| `date` | 日期 | 按需 | 单日记录的业务日期 |
| `status` | 枚举字符串 | 按需 | 内容或事项状态，含义见下文 |
| `tags` | 字符串列表 | 按需 | 主题与检索标签；需要滚动引用的记录按现有映射填写 |
| `aliases` | 字符串列表 | 按需 | 常见别名，用于查找与链接 |
| `project` | 带引号的内部链接 | 按需 | 所属项目的项目说明；只填一个主要归属 |
| `source` | 字符串列表 | 按需 | 外部 URL 或带引号的内部来源链接 |
| `version` | 带引号的字符串 | 按需 | 规范或模板的版本，如 `"1.0"` |
| `period_start` | 日期 | 周期复盘必填 | 周期起始日，含当天 |
| `period_end` | 日期 | 周期复盘必填 | 周期结束日，含当天 |
| `due` | 日期 | 按需 | 明确的截止日期 |
| `privacy` | 枚举字符串 | 按需 | `public`、`personal`、`sensitive`，仅为分类提示 |

新建正式笔记最小示例，以下内容为示例数据：

```yaml
---
title: 听力练习方法
type: knowledge
created: 2026-09-14
---
```

不要追填无法确认的历史创建日期；整理旧笔记时保留已有证据，未知字段可暂缺并在必要时说明。文件修改时间不能自动等同于创建日期或事件日期。

## 4. 文档类型与状态

### 4.1 type 取值

| 取值 | 用途 |
| --- | --- |
| `inbox` | 待整理的收集条目 |
| `project` | 项目或模块说明 |
| `daily` | 普通日常记录 |
| `knowledge` | 知识、方法、规则和工具操作笔记 |
| `research` | 研究与分析 |
| `trade` | 单日交易日志 |
| `review` | 周期复盘 |
| `case` | 案例记录 |
| `template` | 模板原文件 |
| `snippet` | 公共代码片段与使用说明 |
| `dataset` | 公共结构化数据，如引用数据库 |
| `specification` | 架构、管理与格式规范 |

一份笔记只有一个主要类型。`type` 是机器可查询的分类，标签仍可使用中文；不要依赖标签代替类型。

### 4.2 status 取值与使用

| 取值 | 含义 |
| --- | --- |
| `pending` | 已收集，尚待处理 |
| `draft` | 正在编写或验证，内容未定稿 |
| `active` | 正在执行或持续维护；规范表示当前生效 |
| `completed` | 有明确终点的事项完成，或一篇记录已写完 |
| `archived` | 已归档、停止日常维护 |

常见路径是 `pending → draft / active → completed → archived`；允许按实际情况跳转或重新启用。长期知识笔记可以省略状态，避免把所有内容都变成任务。

笔记属性状态描述整篇内容；正文复选框描述具体任务。`completed` 不要求项目内所有关联任务都已完成。模板不得让新建业务记录默认“已完成”。

## 5. 时间格式

- 日期统一为 `YYYY-MM-DD`，例如 `2026-09-14`，不要写 `2026-9-14`、`<2026><7-7>`。
- `created`、`updated`、`date` 等日期字段只使用日期，不混用带时间的字符串。
- 需要精确时刻时，按用途新增 `occurred_at` 等字段，使用带时区的字符串，例如 `"2026-09-14T09:30:00+08:00"`。
- 本库默认记录时区为 Asia/Shanghai；外地事件保留原时区或明确转换后的时区。
- 周期复盘用 `period_start` 和 `period_end` 表达完整范围，不只依赖文件名。开始日不得晚于结束日。
- 修改标题或正文不改变业务日期；实质内容更新才调整 `updated`。

## 6. 标签、链接与来源

标签使用 YAML 列表，不加 `#`，避免同义标签并存。建议选择少量稳定主题；不要把日期、状态、整个文件路径再写成标签。

```yaml
tags:
  - 交易日志
  - 复盘
project: "[[03 财富投资/02 交易系统/项目说明]]"
source:
  - "[[09 知识库管理/LEO知识库构建思路]]"
```

滚动引用现有代码读取 `tags` 并按映射匹配；同时存在多个可匹配标签时，目前采用第一个匹配类别。需要确定显示交易类语录时优先使用 `交易日志`。不要未经修改代码就改变公共数据的类别名称。

外部来源在 `source` 中保存 URL，正文补充作者或机构、标题、发布日期和访问日期（按可获得信息填写）。一个来源只证明其实际支持的内容；摘录、转述与个人推断分别标识。来源不详时如实写明，不猜测作者。

## 7. 模板原件与生成记录

模板原文件可使用 `type: template`，记录自身 `created`、`updated`、`version`；代码片段用 `type: snippet`。这些属性说明模板本身，不应原样作为业务记录属性。

生成记录时：
1. 将 `title` 改为实际标题，`type` 改为目标类型，例如 `trade`。
2. 将 `created` 改为实际创建日期，填写业务 `date` 或周期范围。
3. 将状态改为实际状态，通常为 `draft` 或 `active`。
4. 移除模板维护属性及模板专用标签；需要追踪模板版本时可使用 `template_version: "1.0"`。
5. 清除提示语、演示数据和占位符；保留有实际用途的章节。

本库未确认存在自动字段转换流程，上述步骤按手动复制或插入模板处理。字面占位符仅用于模板提示，不能留在完成的记录中。

## 8. 表格与数值

### 8.1 通用规则

- 同一列只保存同类数据，一行表示一条事件、记录或观察。
- 数值单元格不附带单位、货币符号或千位分隔符；在列名或独立字段中注明单位。
- 百分比列名写明 `（%）`，值 `12.5` 代表 12.5%；比例小数不得与百分数混用。
- 未知值留空；零表示确实为零。已明确“不适用”的情况在备注解释。
- 保留业务所需精度，不提前四舍五入原始数据；展示汇总时说明口径。
- 计算结果注明公式、区间、来源及费用处理方式。多币种金额未换算前不能直接相加。

### 8.2 交易记录建议字段

交易表建议至少包含成交时间、市场、标的代码、标的名称、方向、数量、价格、币种、费用和备注。时间使用带时区时间，市场用于区分相同代码，标的代码作为文本保存以保留前导零。

同一数量列采用同一种单位，股票可用股数；其他品种需要明确份数、手数、合约乘数。买卖方向使用稳定值，如 `buy`、`sell`，展示时可以说明中文含义。一次委托分次成交时按实际成交分别记录，或明确标记为汇总并说明口径。

收益额、收益率、持仓市值不是同一个概念。复盘需说明已实现或未实现、净值时间、费用及汇率；资金出入造成的账户变化不能直接当作投资收益。此处只规范记录格式，不规定交易策略。

### 8.3 YAML 与内联字段的边界

整篇笔记属性放 YAML；重复条目按表格或既有列表格式保存。普通正文不随意使用 `字段::`，避免产生意外的查询字段。新增查询前先定义字段与类型，再编写查询。

## 9. 引用数据库兼容规范

现有滚动引用通过列表文本解析以下字段，保持字段名、顺序和同一列表项内的换行格式：

```text
- 类别:: 学习
  语录:: 每次练习后记录一个可改进之处。
  作者:: 自我提醒
```

上例是格式示例。每条记录只有一个类别、一段单行语录和一个作者字段；作者未知可留空，不编造署名。继续使用现有类别：交易日志、学习、专业、认知、日记、写作。

不要直接改成表格、改字段名或拆成多个列表项，否则现有正则解析可能失效。扩展格式时应同步修改公共片段及实际使用它的笔记，并验证类别匹配、空结果和轮播表现。

## 10. 内容质量与安全

### 10.1 内容质量

- 事实标注来源或观察依据，观点说明推理与适用边界。
- 重要结论保留修订原因，不把过时判断悄悄改成当时已知。
- 同一数据尽量保留一个主记录，汇总通过链接或查询引用。
- 发现重复内容先比较差异、合并有效信息并更新引用，再决定是否归档旧稿。
- AI 生成内容需要区分用户事实、外部材料和生成建议，不能把尚未验证的建议写成用户经历或既定规则。

### 10.2 数据安全

`privacy` 只提供分类提示，不是访问控制。仓库的实际可见性和同步范围应在发布时核对，不根据旧说明推断。

不在笔记、附件或代码中保存密码、令牌、私钥；账户信息、身份资料和健康资料按实际分享范围脱敏。公开同步前检查本次变更及附件，避免夹带已有私人内容。

删除工作区文件不等于移除 Git 历史；发现敏感数据暴露时应停止继续传播并按实际情况处理凭证和历史。备份和 Git 同步分别管理，定期确认备份可恢复。

## 11. 兼容与迁移

已知现状：收件箱模板的 `created` 仍有日期时间占位符，`source` 为旧字符串；日常模板默认 `completed`；交易模板仍有固定示例日期；部分笔记缺少 `type` 或其他基本属性。

这些是待迁移项，本次规范编写未批量修改历史数据或模板。按以下顺序逐步对齐：
1. 新建记录采用新格式。
2. 常用模板按本规范更新，确认生成步骤。
3. 整理活跃项目时补充可确认的字段。
4. 旧记录保留原始信息，不推测缺失值；依赖旧字段的查询先评估再修改。

`source` 从字符串迁移为列表时，同步检查使用它的查询。日期从混合格式迁移时，区分创建时间与业务时间，不直接截断全部时间信息。

## 12. 完成检查

正式记录完成前检查：标题与类型清楚；日期有效；列表和数值类型一致；状态符合实际；占位符已清理；来源可追溯；链接与附件有效；敏感内容符合分享范围。

检查项用于提升可用性，不阻碍临时速记，也不要求为了格式修改与当前任务无关的历史内容。
