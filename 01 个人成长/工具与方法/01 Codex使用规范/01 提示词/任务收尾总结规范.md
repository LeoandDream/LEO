# 任务收尾总结规范 v1.0

当我说「收尾」「总结当前进度」「生成交接记录」时，
不要写普通聊天摘要，而是生成可供下一次 AI 会话直接恢复工作的技术交接记录。

## 1. 当前任务

- 最终目标
- 当前阶段目标
- 当前工作环境 / 平台
- 关键项目路径、环境名、设备

## 2. 本次完成

只记录已经实际完成并验证的事项。

- 做了什么
- 如何做的
- 最终结果
- 验证证据

禁止把“计划做”“可能成功”写成“已经完成”。

## 3. 最终有效方案

保留最终确认有效的方法。
包括：

- 核心配置
- 文件路径
- 参数
- 命令
- 代码
- 网络/系统架构
- 版本信息（如果重要）

代码必须保持可复制执行。

## 4. 排障历史

对于重要故障记录：

### 问题

现象：

### 排查

尝试过什么：

### 根因

最终确定原因：

### 解决

最终有效操作：

### 易错点

以后如何避免：

已经证明无效的方案要明确标记：
❌ 无效 / 已排除
而不是让下一次 AI 再重复尝试。

## 5. 当前系统状态

明确记录此刻真实状态，例如：

| 组件 | 状态 | 关键参数 |
| --- | --- | --- |
| Windows Clash | ✅ | 127.0.0.1:7897 |
| SSH Tunnel | ✅ | remote 17891 → local 7897 |
| VS Code Extension Host | ✅ | HTTP_PROXY=17891 |
| Codex | 待验证 | ... |

状态统一：
✅ 已验证
⚠️ 部分完成 / 存疑
❌ 已确认失败
⏳ 尚未进行

## 6. 未完成事项

按照优先级记录：
P0：
P1：
P2：

不要混入已经完成的任务。

## 7. 下一次会话起点

这是最重要的部分。

明确告诉下一个 AI：

- 不需要重新做什么
- 第一件应该做什么
- 从哪条命令/哪个文件/哪个实验继续
- 成功判据是什么

## 8. 关键上下文

只保留下一次工作真正需要知道的信息：

- 为什么采用当前方案
- 已经排除哪些路线
- 用户做出的关键决定
- 不应再次询问的已知信息

## 9. 可复用 SOP

如果本次产生了以后会重复使用的流程，则整理：
Step 1
Step 2
Step 3
...

如果只是一次性任务，则省略。

## 10. 给下一次 AI 的交接指令

用 5~15 行高度压缩地描述：
「你正在接手什么、目前做到哪里、下一步是什么、哪些东西不要重复做。」

# 输出风格

1. 中文为主，技术名词保留英文。
2. 高信息密度，避免聊天式废话。
3. 结论优先，原因随后。
4. 命令、路径、参数必须精确保留。
5. 不重复解释已经明确的基础知识。
6. 区分“事实 / 已验证结果 / 推测 / 下一步计划”。
7. 对重要数字、端口、PID、路径、版本不得自行猜测。
8. 长项目优先保证“下次能恢复工作”，而不是追求文章可读性。
9. 对排障任务必须保留「错误现象 → 根因 → 最终解决方案」。
10. 如果发现旧总结与本次实际结果冲突，以本次已验证结果为准，并明确更新。
